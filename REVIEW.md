# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–38) | 1. Ignored IST timezone and R1 whole-second truncation (assumed `punch_in` was naive local time).<br>2. Grace period condition was incorrect: Rule R2 states late only if strictly > 10:00 (600 seconds) after `shift_start`. Doing integer division on minutes caused punches like 09:40:01 to yield 10 minutes, failing `minutes > 10`.<br>3. Failed to handle shift start date reference correctly (e.g. overnight shifts starting on the attendance date). | A punch-in at 09:40:05 IST returned 0 late minutes instead of 10. Naive UTC punches produced wildly incorrect or negative values. | Localized `punch_in` to IST with whole-second truncation per R1, constructed `shift_start` timestamp using the record's `attendance_date` in IST, checked `diff_seconds > 600`, and floored elapsed minutes (`diff_seconds // 60`). |
| 2 | `compute_work_hours` (lines 40–41) | Used Python's built-in `round()`, which applies banker's rounding (round half to even) on IEEE-754 floats, and did not truncate instants to whole seconds per R1. Rules R4 & R8 explicitly mandate rounding to 2 decimals half-up (`ROUND_HALF_UP`), not banker's rounding. | An exact elapsed duration resulting in `4.125` hours rounded down to `4.12` instead of rounding up to `4.13`. | Truncated instants to whole seconds per R1, calculated hours as exact Decimal quotient of seconds / 3600, and rounded using `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 3 | `compute_overtime` (lines 44–48) | 1. Rule R3 specifies overtime is counted **only when >= 30 minutes**; otherwise 0. The starter returned any positive difference (`max(0, ...)`), awarding overtime for 5 or 20 minutes.<br>2. Failed to handle overnight shifts (where `shift_end <= shift_start`), causing `shift_end` to be evaluated on the attendance date instead of the next calendar day per R1.<br>3. Did not truncate seconds per R1 or normalize naive/UTC timestamps. | Punching out 15 minutes after shift end returned 15 overtime minutes instead of 0. For overnight shifts (e.g. 22:00-06:00), punch-out in the morning produced negative or huge values. | Added overnight shift check (`end_dt += timedelta(days=1)` if `shift_end <= shift_start`), truncated to whole seconds per R1, and enforced the `>= 30` minute threshold (returning 0 if `< 30`). |
| 4 | Instant / Epoch Millis serialization & validation (entire file) | Instants (`created_at`, `punch_in`, `punch_out`, `punched_at`) were accepted as arbitrary ints/floats or naive datetimes and serialized directly as Python datetimes or ISO strings. The contract requires all instants across all endpoints to be integer epoch milliseconds (`100000000000 <= val <= 4102444800000`), with smaller seconds-like values rejected with 422. MongoDB stores BSON UTC datetimes; API must return integer epoch ms. | Passing values `< 100000000000` was accepted; responses returned ISO datetime strings or failed JSON serialization instead of integer epoch ms. | Added Pydantic field validators enforcing `ge=100000000000, le=4102444800000`, helper functions `epoch_ms_to_datetime()` (with R1 second truncation) and `datetime_to_epoch_ms()`, converting at the API boundary. |
| 5 | Database Indexes & Startup Lifecycle (lines 22–24) | No database indexes were created. The specification requires indexes to be created at startup idempotently, specifically unique indexes to guarantee concurrency safety and compound indexes so that `/admin/explain` uses `IXSCAN` and no `COLLSCAN` on large datasets. | Concurrent identical creations or punch-ins resulted in duplicate documents; queries on 100k records fell back to slow `COLLSCAN`. | Added FastAPI lifespan context manager creating: unique index on `employees.emp_code`, unique compound index on `attendance_logs.(emp_code, date)`, index on `employees.department`, and indexes on `attendance_logs.(date, emp_code)` and `attendance_logs.status`. |
| 6 | `create_employee` (lines 77–86) | 1. Check-then-insert race condition (`find_one` followed by `insert_one`) allowing concurrent requests with identical `emp_code` to bypass validation.<br>2. Missing validation: `shift_start` must differ from `shift_end` (per OpenAPI line 119), and missing format validations for `emp_code` (`^EMP\d{4,6}$`) and email.<br>3. `created_at` stored as naive local `datetime.now()` and returned as datetime rather than epoch milliseconds. | Concurrent POSTs inserted duplicates; identical shift start and end was allowed; `created_at` returned ISO string instead of integer epoch ms. | Handled concurrency by catching `DuplicateKeyError` from the unique index to return 409; added Pydantic validators for `emp_code`, email, and `shift_start != shift_end`; stored UTC BSON date and returned integer epoch ms. |
| 7 | `list_employees` (lines 88–96) | 1. Pagination bug: `skip = page * page_size` skips the first page entirely (e.g. `page=1` skipped 20 items instead of 0).<br>2. `total` counted the whole collection (`count_documents({})`) regardless of `department` filter.<br>3. Missing sorting: OpenAPI requires results sorted by `emp_code` ascending.<br>4. `created_at` was not formatted as epoch milliseconds. | Requesting `page=1` returned the second page of employees; filtering by department showed the count of all employees in the DB; results had undefined sort order. | Fixed pagination offset to `skip = (page - 1) * page_size`, updated count to `count_documents(q)`, added `.sort("emp_code", 1)`, and serialized `created_at` to integer epoch ms. |
| 8 | `punch_in` (lines 99–123) | 1. Check-then-insert race condition (`find_one` then `insert_one`) allowed duplicate punch-ins for the same date.<br>2. Non-existent `emp_code` resulted in 500 error (`emp["shift_start"]` on `None`) instead of 404.<br>3. Calendar date extraction `ts.date().isoformat()` used server local time instead of IST calendar date per R1 (and missed overnight shift date assignment where punch-in before `shift_end` belongs to previous day).<br>4. `status` accepted invalid strings (must be restricted to `PRESENT`, `WFH`, `ON_DUTY`).<br>5. Returned internal `id` (`ObjectId`), which the contract explicitly forbids. | Concurrent punch-ins created two records; unknown employee threw 500; invalid status accepted; response contained forbidden `"id"` field. | Returned 404 if employee missing; computed IST attendance date including overnight shift logic; relied on `(emp_code, date)` unique index catching `DuplicateKeyError` to return 409; validated status enum; returned contract-compliant schema without `id`. |
| 9 | `list_attendance` (lines 124–150) | 1. In-memory loading: `docs = list(db.attendance_logs.find(q))` loaded entire collection into Python memory before sorting and slicing. Breaks contract requirement: *"Must stay fast on ~100,000 records; do not load the collection into memory."*<br>2. Sorting: sorted only by `date` desc; contract requires `date` descending, then `emp_code` ascending.<br>3. Missing validation: `date_from > date_to` must return 422.<br>4. Returned forbidden `"id"` field and unformatted BSON datetimes. | Calling `/attendance` with 100k records consumed huge memory and CPU; ties on `date` returned non-deterministic order; invalid date range returned 200 with empty list. | Added MongoDB native `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)`; raised 422 if `date_from > date_to`; converted datetimes to epoch ms and omitted `_id`/`id`. |

Also note anything you looked at and decided was **not** a defect, and why.
- **`status` defaulting to `PRESENT` in punch-in**: OpenAPI schema specifies `default: PRESENT`, so the default assignment in the starter code is intentional and correct.
- **`IST = timezone(timedelta(hours=5, minutes=30))`**: Defining IST as UTC+05:30 matches rule R1 specifications.
